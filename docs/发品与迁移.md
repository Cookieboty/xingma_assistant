# 发品流程与微信笔记迁移

## 1. 业主发品逻辑（产品）

业主侧发品是 **「基于图片发品」**：

1. 上传一组商品图（上身/平铺/细节等）。
2. 其中 **至少一张是商品吊牌/标签照片**。
3. 吊牌上的文字即结构化字段来源：
   - 【款号】→ `products.style_no`
   - 【成分】/【材质】→ `products.material`
   - 【款式】→ `products.name`（及标签）
   - 【克重】→ 写入描述/标签（首期无独立列）
   - 【颜色】→ 拆成 SKU `color`
   - 【尺码】→ 拆成 SKU `size`

首期实现可以：

- **迁移路径**：直接使用已有微信笔记文本 + 同笔记关联图片落库（本文档 §2），OCR 后续再做。
- **在线发品路径**（后续）：上传图片 →（可选）OCR 吊牌 → 人工确认字段 → 生成 Product + ProductSKU → 媒体入租户目录。

颜色按 `/` 或空白拆分；尺码按 `-`/`－` 或空白拆分；笛卡尔积生成 SKU，编码 `{款号}-{颜色}-{尺码}`（缺省段用 `NA`）。

## 2. 微信笔记 → 本地库迁移（已执行脚本）

### 数据源

- 微信收藏目录：`.../xwechat_files/lgd_lc_afe5/business/favorite/`
- 笔记文本：`temp/NoteCache/temp_{batch}_{idx}_0.htm`
- 关联图片：`temp/NoteCache/微信图片_{batch}_{idx}_*.jpg`
- 样本/结果：`docs/wechat_notes_sample.json`、`docs/wechat_notes_import_report.json`

### 图片关联策略

1. **主策略（精确）**：同一 NoteCache 批次前缀 + 笔记序号  
   `temp_{batch}_{idx}_0.htm` ↔ `微信图片_{batch}_{idx}_*.jpg`
2. **同款去重**：同一款号出现多条笔记时，保留关联图片更多的一条。
3. **未归类**：`temp/` 与 `NoteCache/` 中其余「微信图片_*」（指纹未落入上述关联集）拷贝到  
   `backend/storage/tenants/tenant_dev_001/products/_unclassified/`，并在导入报告中计数说明。  
   不猜测映射，避免错挂到款。

### 落盘与 URL（本地，不上 OSS）

- 文件：`backend/storage/tenants/tenant_dev_001/products/{款号}/01.jpg …`
- `media_assets.provider = local`
- `media_assets.object_key = tenants/tenant_dev_001/products/{款号}/xx.jpg`
- 访问：后端将 `storage/` 挂到 `/media/`，即 `http://127.0.0.1:3000/media/{object_key}`
- 商品 `cover_media_ids` 指向对应 `media_assets.id`

生产环境仍走 OSS/COS + 短时签名（见《技术方案》§6）；本迁移明确 **不上传 OSS**。

### 脚本

```bash
cd backend
node scripts/import_wechat_notes.mjs
```

依赖 `backend/.env` 的 `DB_*`（勿把密钥写进文档或报告）。默认租户 `tenant_dev_001`，商品等级 `pl_open`（公开款）。

### 验证

- SQL：`products` / `product_skus` / `media_assets` 计数
- 磁盘：各款目录图片数 + `_unclassified` 数量
- API（可选）：假登录 staff 后 `GET /api/products`

## 3. 与技术方案的关系

- 多租户隔离、分享鉴权不变。
- 本地 `/media` 仅开发/迁移期；上线后列表/详情仍应先鉴权再签发访问（本地也可改为鉴权后重定向到静态路径）。
- OCR 吊牌识别列入后续迭代，不阻塞首期用笔记文本导入。
